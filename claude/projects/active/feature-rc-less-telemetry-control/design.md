# Design: GCS / Datalink-Heartbeat Failsafe

**Project:** feature-rc-less-telemetry-control
**Author:** Developer
**Date:** 2026-07-22
**Status:** APPROVED for implementation (2026-07-22). Formal Security Analyst review
was considered and **dropped** — this change has no crypto/auth/network-attack surface;
its risk is safety-correctness, gated by SITL failsafe testing + normal `inav-code-review`.
**Deliverable type:** Design/feasibility. Implementation follows the normal dev workflow.

## 1. Purpose

Give INAV a second, independent link-liveness detector — a GCS/datalink-heartbeat failsafe modeled on PX4 "data link loss" and ArduPilot `FS_GCS_ENABLE`. The goal is to let an aircraft be flown under telemetry-link + autonomous-nav control **without continuously streaming RC frames** and **without a companion computer whose only job is to fake RC**, while still retaining a genuine link-loss safety response.

This document traces how INAV's failsafe liveness works today, states the gap precisely, surveys the two reference implementations, and records the composition and settings decisions (§8). It intentionally stops short of code; implementation follows via the normal dev workflow.

## 2. Problem recap

- The only existing RC-less path is `receiverType = MSP` (`RX_TYPE_MSP`), which requires a **continuous stream of MSP RC frames** to keep the link "alive." On a constrained telemetry link that stream is pure overhead when the RC content is effectively null.
- In practice that stream gets generated by bolting on a companion computer (e.g. an ESP32) — a hardware workaround for what is fundamentally a software limitation.
- What is missing is not "permission to fly RC-less" (see §7 — that is already trivially possible and this feature does not gate it). What is missing is a firmware mechanism that watches the *telemetry link itself* for liveness, so RC frames are not needed at all.

## 3. How INAV failsafe liveness works today (traced)

- The failsafe state machine tracks link state as a single enum `rxLinkState ∈ {FAILSAFE_RXLINK_DOWN, FAILSAFE_RXLINK_UP}` — `inav/src/main/flight/failsafe.h:116-119`, stored in `failsafeState` (`failsafe.h:160`).
- The public liveness query is a one-liner: `failsafeIsReceivingRxData()` returns `rxLinkState == FAILSAFE_RXLINK_UP` — `inav/src/main/flight/failsafe.c:287-290`.
- `rxLinkState` is driven **only** by two functions:
  - `failsafeOnValidDataReceived()` — `failsafe.c:309-315`. Stamps `validRxDataReceivedAt = millis()` and, after `rxDataRecoveryPeriod` (200 ms, `PERIOD_RXDATA_RECOVERY`) of continuous validity, sets `rxLinkState = FAILSAFE_RXLINK_UP`.
  - `failsafeOnValidDataFailed()` — `failsafe.c:317-323`. After `rxDataFailurePeriod` (200 ms, `PERIOD_RXDATA_FAILURE`) of continuous failure, sets `rxLinkState = FAILSAFE_RXLINK_DOWN`.
- Those two functions are called from **exactly one site**: `inav/src/main/rx/rx.c:544-548`:
  ```c
  if (rxFlightChannelsValid && rxSignalReceived) {
      failsafeOnValidDataReceived();
  } else {
      failsafeOnValidDataFailed();
  }
  ```
- The arming interlock consumes the same signal: `ARMING_DISABLED_RC_LINK` is enabled/disabled purely on `!failsafeIsReceivingRxData()` — `inav/src/main/fc/fc_core.c:221-227`.

**Consequence:** INAV has exactly one liveness source (RC frame validity), and both failsafe *and* the arm gate read it through the same boolean. There is no seam today for "the link is alive because the GCS is talking to me."

## 4. Reference implementations

### ArduPilot — `FS_GCS_ENABLE`
- A GCS failsafe distinct from the RC (throttle/RC) failsafe. Triggered when MAVLink heartbeats from the GCS stop arriving for `FS_GCS_TIMEOUT` (default ~5 s).
- Configurable *reaction* (disabled / RTL / SmartRTL / Land / continue-if-in-auto), independent of the RC failsafe reaction.
- Independently enable-able: a vehicle can run GCS failsafe with or without an RC failsafe.

### PX4 — data link loss
- `COM_DL_LOSS_T` (data link loss timeout) plus a configurable reaction (`COM_DLL_REACT` family): hold / RTL / Land / Terminate.
- Liveness comes from the telemetry link heartbeat, entirely separate from the RC-loss (`COM_RC_LOSS_T`) path.

**Takeaway shared by both:** the GCS/datalink failsafe is an *additive, independent* liveness source with its own enable + timeout + reaction. It never replaces the RC failsafe; the two coexist and a user chooses which are active. This is exactly the shape requested for INAV.

## 5. The gap, stated precisely

INAV needs a second liveness input feeding the failsafe decision, sourced from telemetry-link heartbeat activity rather than RC frame validity, that:
1. can trigger the existing `failsafe_procedure` on loss, and
2. is enabled/timed independently of the RC-link source, and
3. can, when the operator chooses, satisfy the arm gate / keep the aircraft flying with **no RC frames streamed at all**.

## 6. Proposed design

### 6.1 Shape: additive liveness source, not a rewrite
- Introduce a GCS-liveness tracker parallel to the RC one. Keep `rxLinkState` semantics for RC untouched; add a sibling concept `gcsLinkState` (or a `lastGcsHeartbeatAt` timestamp evaluated against a timeout).
- Do **not** repurpose `failsafeOnValidDataReceived/Failed`. Add `failsafeOnGcsHeartbeat()` (stamps `lastGcsHeartbeatAt = millis()`) and evaluate staleness in the failsafe update loop (`failsafeUpdateState`, `failsafe.c:400`).

### 6.2 Heartbeat transport — where "last seen" comes from
Two candidate sources; the design should support MSP first, MAVLink as a follow-on:
- **MSP activity on the configured RX/telemetry port(s) (DECIDED for v1).** `mspPort_t.lastActivityMs` already exists (`inav/src/main/msp/msp_serial.h:88`, updated on every received command at `msp_serial.c:460`). A GCS polling telemetry over MSP naturally refreshes this.
  - **Decision (product owner, 2026-07-22):** the heartbeat is "any MSP command received **on a configured RX and/or telemetry port** within the timeout." It is explicitly **not** global `lastActivityMs` across all MSP ports — other things (a USB Configurator session, a bench tool, a passthrough) can emit MSP without being the flight control link, and those must not count as liveness. Implementation must therefore resolve which `mspPort_t`(s) correspond to the configured RX/telemetry serial function(s) and only consult those.
  - A **dedicated MSP heartbeat message is deferred, not rejected** — it can be arranged later and would let a GCS assert liveness explicitly rather than incidentally. For v1, "any command on the designated port(s)" is accepted with a documented caveat that incidental/automated polling on that port also refreshes liveness.
- **MAVLink heartbeat (follow-on).** True `HEARTBEAT` (and/or `MANUAL_CONTROL`) RX. Mainline INAV MAVLink is effectively TX-only (`handleMAVLinkTelemetry`, `inav/src/main/telemetry/mavlink.c:37`; no inbound heartbeat parsing found in tree, 2026-07-22). This path depends on the inbound-MAVLink work tracked on the `mavlink_multiport2` branch and should be scoped against it rather than duplicated.

### 6.3 Composition with the RC-link source — THE key decision
The failsafe "is my control link alive?" question becomes a function of two sources. Options:

- **Option A — OR of enabled sources (recommended).** Link is considered UP if *any enabled* source is fresh. Failsafe triggers only when *all enabled* sources are stale.
  - Matches operator intent: "I run on GCS heartbeat, RC is optional."
  - The arm gate (`ARMING_DISABLED_RC_LINK`) must then read the composed liveness, not `failsafeIsReceivingRxData()` alone, or renamed to reflect "any control link."
- **Option B — per-source independent failsafe.** Each source can independently push the aircraft into failsafe. Closer to ArduPilot's separate FS reactions, but heavier and can produce confusing double-trigger semantics with INAV's single `failsafe_procedure`.
- **Option C — RC primary, GCS as fallback only.** GCS liveness only matters when RC failsafe is disabled. Simplest but least flexible; effectively a special-case of A.

**Decision: Option A** (D1), with a single shared `failsafe_procedure`. It is the smallest change that delivers the requested behavior and keeps one failsafe reaction path.

### 6.4 Settings surface (new, independent)
New `failsafeConfig` fields (PG `failsafeConfig_t`, `failsafe.h:32-49`; exposed via `settings.yaml`):
- `failsafe_gcs_link_enabled` (bool, default OFF) — enable the GCS heartbeat as a liveness source.
- `failsafe_gcs_link_timeout` (ms or 0.1 s steps; default ~5 s to match ArduPilot) — staleness threshold.
- `failsafe_gcs_link_source` (enum: MSP / MAVLINK / ANY) — which transport feeds the heartbeat; MAVLINK gated on the inbound-MAVLink capability existing.
- The existing RC-link failsafe stays enabled by default and unchanged. Both sources are independently toggleable.
- **Config-time guard — advisory only (DECIDED).** If both RC-link and GCS sources end up disabled, the aircraft has *no* automatic link-loss response. Product-owner decision (2026-07-22): **no hardcoded minimum-one-source requirement.** Permitted (operator's onus, §7); the Configurator/CLI should warn loudly but must not hard-block.

### 6.5 Arming interaction — DECIDED: option (b), separate flag
- **Decision (product owner, 2026-07-22): add a parallel `ARMING_DISABLED_GCS_LINK` flag** rather than re-expressing `ARMING_DISABLED_RC_LINK`. Rationale: auditability — the arming-blocked reason shown to the user distinguishes "no RC link" from "no GCS link," and each flag maps 1:1 to a real source.
- **Important composition caveat.** `isArmingDisabled()` ORs all `ARMING_DISABLED_*` flags (`fc_core.c` / `runtime_config.h:81`) — so if `ARMING_DISABLED_RC_LINK` and `ARMING_DISABLED_GCS_LINK` were each raised independently whenever their own source is stale, the result would be **AND** semantics (both links required up), which contradicts the Option-A "any enabled source up" intent. Therefore:
  - Each flag is raised only when its source is **enabled**. A disabled source never raises its flag.
  - To preserve "any enabled source satisfies the gate," the two link flags are **not** fed to `isArmingDisabled()` naively. Instead, compute a single composed predicate `anyEnabledControlLinkUp` = (RC enabled && RC fresh) || (GCS enabled && GCS fresh) || (no link source enabled at all → allowed, per the no-hard-minimum decision), and gate arming on that. The individual `ARMING_DISABLED_RC_LINK` / `ARMING_DISABLED_GCS_LINK` flags remain for **display/telemetry only** (which link is down), not as independent hard blocks.
  - This split — hard-gate on the composed predicate, `ARMING_DISABLED_*` link flags informational for UX — is the decided approach (D3). During code review, verify no consumer treats a raised `ARMING_DISABLED_RC_LINK` as an independent arming block (see §8 watch items).
- No other arm gate is weakened. Throttle/level/geozone/sensor gates are untouched.

### 6.6 Failsafe procedure reuse
- On composed-liveness loss, drive the **existing** `failsafe_procedure` (AUTO_LANDING / DROP / RTH / NONE, `failsafe.h:122-126`) through the existing state machine. No new procedure types. This keeps RTH/land behavior, min-distance logic, and WP-mission delay handling identical to today.

## 7. Safety analysis & honest caveats
- **This is not a safety guardrail and must not be sold as one.** An always-on inertial RC spoofer (an ESP32 that arms, goes to angle, throttles up, switches to WP at altitude, and keeps sending RC regardless of link state) already lets anyone fly fully RC-less *today*. This feature does not create that capability and does not gate it.
- **The safety value is realized only when the operator keeps at least one liveness source enabled.** The feature's worth is that it replaces the "dumb, always-on spoofer" (which cannot detect link loss) with a firmware mechanism that *does* detect link loss and reacts. That is a genuine improvement over the ESP32 hack — but only if enabled.
- **Both-sources-disabled is a valid but dangerous config.** Consistent with the requested "onus on the user" stance. Mitigation is a loud Configurator/CLI warning, not a hard block, because a hard block would just push users back to the spoofer.
- **MSP "any activity" heartbeat is coarse.** Unrelated/automated polling could keep the link "alive" even if the human GCS has logically stopped commanding. Documented caveat for v1; a dedicated heartbeat command is the planned clean fix if the coarse version proves inadequate in testing.
- **No new remote-arming surface.** The design does not add a network path that can arm the aircraft that did not already exist via MSP; it changes when the existing arm gate is satisfied.

## 8. Decisions & implementation-time watch items

**Settled decisions (product owner, 2026-07-22):**
- **D1 — Composition:** Option A (§6.3). Any *enabled* source fresh → link UP; failsafe fires only when all enabled sources are stale. Single shared `failsafe_procedure`.
- **D2 — Heartbeat source (§6.2):** any MSP command **on the configured RX/telemetry port(s)** (not global MSP activity). Dedicated MSP heartbeat message deferred, not rejected.
- **D3 — Arming (§6.5):** separate `ARMING_DISABLED_GCS_LINK` flag for display; arming hard-gated on a single composed `anyEnabledControlLinkUp` predicate.
- **D4 — No hard minimum (§6.4, §7):** no hardcoded minimum-one-source requirement. Advisory Configurator/CLI warning only; no hard block.
- **D5 — Defaults:** GCS failsafe **default OFF**; `failsafe_gcs_link_timeout` **default 5 s** (matches ArduPilot).

**Watch during implementation / code review / SITL testing (not gates, just don't botch them):**
- The D3 split means a raised `ARMING_DISABLED_RC_LINK` no longer implies arming is blocked on its own. Check any OSD/telemetry arm-reason display that assumes the old meaning and update it.
- The D2 caveat: incidental/automated MSP polling on the designated port refreshes liveness and could mask a logically-dead GCS. Documented user caveat for v1; the dedicated heartbeat message is the clean fix later.
- Resolving "which `mspPort_t` is the configured RX/telemetry link" must not misidentify a port in shared/passthrough configs (false-sustain or false-drop of liveness). Cover this in SITL testing.

## 9. Recommendation
- **This is a genuine firmware feature, not docs-only.** No existing mechanism supplies telemetry-link liveness; §3 shows the single-source design has no seam for it.
- Implement as an **additive GCS-heartbeat liveness source (Option A)** feeding the existing failsafe procedure, MSP-activity-sourced first, MAVLink heartbeat as a follow-on aligned with `mavlink_multiport2`.
- All design decisions are settled (§8, D1–D5). Ready to implement via the normal dev
  workflow; the real gate is SITL failsafe testing + `inav-code-review`, not a security review.
